# 1. 备选路径比较

在 `docs/04_Architecture.md` 1.3 节已经说明了"为什么不是单 Agent + 工具调用"，
本章从资源约束角度，把当时实际存在的几条路径摆在一起比较。

## 1.1 政策匹配：确定性规则 vs 向量检索（RAG）

| 维度 | 确定性规则匹配（已选） | 向量检索（ChromaDB 等） |
|---|---|---|
| 实现成本 | 低——直接复用已经结构化的证据字段做 if 判断 | 中高——需要 embedding、chunking、相似度阈值调优 |
| 可审计性 | 高——`rule_hits` 精确对应政策编号，可直接追溯 | 低——检索返回"相似片段"，仍需额外映射回精确编号 |
| 适用语料规模 | 当前 4 个政策文件、几十条编号条款，规模小、结构清晰 | 语料规模大、非结构化程度高时优势才明显 |
| 与业务论点的一致性 | 与 `docs/03_BenchmarkResearch.md` 引用的阿里云一线经验一致："订单财务类场景不应让模型自由检索判断" | 与该论点相反 |

**结论**：选择确定性规则匹配。这不是资源不足下的妥协，而是在当前政策语料规模
和"决策必须可审计"的约束下，向量检索本身不具备优势——加了反而会引入新的不
确定性来源（检索排序漂移）而不解决任何现存问题。

## 1.2 决策方式：置信度自由裁决 vs 声明式规则引擎

| 维度 | 声明式规则引擎（已选） | LLM 自由裁决 |
|---|---|---|
| 结果可复现性 | 高——同样输入永远同样输出，`data/decision_rules.json` 变更前后可对比 | 低——同一输入多次调用可能不同结果 |
| 金额计算安全性 | 高——`unit_price_times_quantity` 等表达式硬编码计算方式，不可能算错 | 依赖模型数学能力和 Prompt 约束，存在幻觉风险 |
| 新规则上线成本 | 低——改 JSON 配置文件，不改代码，见 `docs/05_DecisionRules.md` | 需要重新调 Prompt 并验证，成本更高且难以验证充分性 |
| 处理"信息不完整、口径不统一"的能力 | 弱——遇到规则未覆盖的组合会显式路由到 Reflection，不会硬给结果 | 强——但"强"的代价是结果不可控 |

**结论**：核心裁决用声明式规则引擎，LLM 只负责意图理解和话术生成两类"错了
代价可控、可以人工兜底"的环节。这个分工在 `docs/04_Architecture.md` 1.3 节
已有架构层面的说明，本节补充的是"为什么这是资源约束下的正确取舍"：声明式
规则引擎的开发成本在项目周期内可控，且验证成本远低于"证明一个 LLM 裁决系统
在所有输入下都不会出错"。

## 1.3 履约执行：同步直接调用 vs 异步任务 + Worker

| 维度 | 异步任务 + 独立 Worker（已选） | 同步直接调用外部服务 |
|---|---|---|
| 失败处理 | 幂等重试、指数退避，失败不影响已记录的裁决结论 | 调用失败需要在裁决请求内联处理，容易把"业务判断错误"和"外部服务抖动"混在一起 |
| 可观测性 | `action_tasks`/`outbox_events` 独立可查，能看到"批准了但还没执行"这个中间态 | 中间态不落盘，难以事后排查 |
| 部署复杂度 | 需要额外一个 Worker 进程 | 无需额外进程 |

**结论**：选择异步任务模式，代价是多一个需要独立启动的服务（`docker-compose.yml`
的 `action-worker`，见第 3 章），换来的是"批准"和"退款已经到账"两个概念在系统里
被严格区分——这正是 `docs/10_ResultsReport.md` 2.4 节记录的那次真实运维教训
（Worker 未启动导致申请卡在 `ExecutionPending`）从反面印证了这个分层是必要的：
问题出在"忘记启动 Worker"这个运维环节，而不是"系统把批准和到账混为一谈"这个
设计环节——分层本身把错误限制在了可观察、可修复的范围内。

# 2. 资源约束下的取舍

以下取舍由开发资源约束直接决定：

- **Mock Database 覆盖度优先于规模**：`docs/02_DataDesign.md` 2.3 节的场景矩阵
  只构造了刚好覆盖每个决策分支的订单记录（21 条 Ground Truth），而不是追求
  更大的样本量——用有限的构造成本换取"每条分支都被真实触发过"这个更重要的
  保证。
- **LLM-as-Judge 样本量克制在 7 条**：真实模型调用有费用和时间成本，7 条用例
  的目标是覆盖已知最容易出问题的场景类型（问候语、日期先后判断、多问句、
  口语化表达），而不是穷举所有对话变体，见 `docs/10_ResultsReport.md` 第 4 章
  对这个局限性的说明。
- **不做压力/负载测试的性能优化**：情景推演和并发正确性验证（见
  `docs/07_Evaluation.md` 第 6 章）优先于吞吐量/延迟压测——在没有真实流量画像
  之前，性能优化的目标函数本身是不确定的，投入产出比低于先把正确性和一致性
  做扎实。

# 3. 落地路径设计

## 3.1 环境分层（已经用 docker-compose profile 实现）

| Profile | 服务 | 用途 |
|---|---|---|
| 默认（无 profile） | postgres / backend / frontend | 基础演示，履约动作只会创建任务，不会真正执行 |
| `execution` | + action-worker | 完整闭环，履约任务会被真正认领执行 |
| `test` | + postgres-test / integration-tests | 验证真实 Postgres 事务、约束和并发行为，不污染开发数据 |

这个分层本身就是一条从"看得见流程"到"流程真正跑通"再到"验证过并发正确性"
的递进路径，不需要额外的部署脚本改造。

## 3.2 如果要接入真实外部系统的推荐路径

1. **影子模式（Shadow）**：Worker 的 `PAYMENT_REFUND_URL` 等环境变量先指向
   一个只记录请求、不真正扣款的沙箱端点，观察系统产生的履约任务是否符合预期，
   不改变任何真实业务状态；
2. **小额自动化 + 人工复核并行**：把 `business_rules.json` 的 `high_value_amount`
   临时调低到一个较小的金额，让绝大多数订单先走强制人工路径，只放开小额、
   低风险场景走全自动，同时保留人工复核作为校验对照组；
3. **按规则命中类型放量**：优先放开"未发货取消"（`cancel_unshipped`，唯一
   不依赖任何证据材料的自动批准路径）等确定性最高的规则类型，证据类规则
   （`quality_evidence`/`damage_with_verified_evidence`）放在后面，因为它们
   依赖的"材料审核"环节目前还是机审 + 人工复核的组合，置信度天然更低；
4. **全量放开前重新校准风险阈值**：见 `docs/08_RiskDriverAnalysis.md` 第 2 章，
   `high_refund_count`/`high_value_amount` 等阈值需要基于真实订单金额分布
   重新校准，不能沿用当前未经验证的固定值。

## 3.3 责任矩阵

| 职责 | 归属 | 涉及产物 |
|---|---|---|
| 业务规则参数（阈值、金额、天数） | 业务/风控负责人 | `data/business_rules.json`，改动不需要碰代码 |
| 裁决规则逻辑（新增/修改规则） | Agent 研发工程师 | `data/decision_rules.json` + `docs/05_DecisionRules.md` |
| 政策条款内容 | 政策/合规负责人 | `data/knowledge_base/*.md` |
| Evidence Gate 的安全边界（何时必须转人工） | Agent 研发工程师 + 风控负责人共同确认 | `src/backend/graph/evidence_gate.py` |
| 外部系统对接（支付/仓储/订单取消） | 集成工程师 | Worker 的三个 `*_URL` 环境变量 |
| 人工复核 SOP | 客服主管 | Staff 工作台操作，`docs/06_LowLevelDesign.md` 5.4 节 |
| 评测基线维护 | Agent 研发工程师 | `docs/07_Evaluation.md`，任何规则变更后重跑确定性套件 |

这张表的核心分工原则：**能用配置文件表达的业务判断（规则、阈值、政策文本）
交给对应业务角色维护，不需要懂 Python；只有"安全边界该设在哪"这类需要理解
系统行为的决策，才需要工程师和业务角色共同确认。**这也是选择声明式规则引擎
（而非把所有逻辑硬编码进 Prompt 或 Python）在组织协作层面的直接收益。
