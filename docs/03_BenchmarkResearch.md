# 2. Salesforce Agentforce

## 2.1 核心机制

**决策流程（Atlas Reasoning Engine）**：输入处理（NLP 识别意图与情绪）→ 决策智能（检索信息 → 验证条件 → 制定策略）→ 执行动作。这个"检索 → 验证 → 决策"的三段式结构，与本项目 Order/Logistics/Policy Agent 分头取证、Decision Engine 统一裁决的思路方向一致，但 Agentforce 的"验证"环节封装在单一推理引擎内部，不是拆分给独立 Agent。

**升级机制**：系统只在置信度不达标或客户明确要求人工时才升级；同时存在一类**不因置信度而豁免的强制升级**——大额退款、合同变更等涉及法律或财务风险的场景，即使 Agent 判断置信度很高，也必须升级人工，这被明确定义为"设计上的边界，而非系统失败"。

**动态情绪评分**：OpenTable 团队在 Agentforce 上的实现里，每通对话有一个基线分数，会随客户情绪、措辞（如全大写、要求转人工）实时调整，用这个动态分数决定继续处理、创建工单还是升级人工。

## 2.2 与本项目架构的对照

| Agentforce 设计 | 本项目对应设计 | 差异 |
|---|---|---|
| 置信度不达标才升级 | Reflection Trigger① Confidence Trigger | 思路一致 |
| 大额/合同变更强制升级，不因置信度豁免 | Reflection Trigger③ High-risk Business Rule Trigger | 思路一致，验证了本项目"高置信度不能豁免风险规则"这一设计并非过度设计，而是行业通行做法 |
| 检索 → 验证 → 决策，封装在单一推理引擎内 | Order/Logistics/Policy Agent 独立取证，Decision Engine 统一融合 | **本项目的差异化点**：把"验证"环节拆成多个职责独立的 Agent 各自产出带置信度的证据，而不是让单一引擎内部黑盒处理，这让"证据从哪来、权重多少"更可追溯、可审计 |
| 动态情绪评分驱动升级 | 不建模独立情绪评分维度；本项目升级判断完全基于业务事实（金额、证据状态、历史行为）而非语气/情绪信号，避免升级依据难以审计 | 差异化选择：业务事实驱动升级比情绪驱动升级更适合本项目"决策需可解释、可追溯"的定位 |

# 3. Intercom Fin AI

> 2026年6月15日，Salesforce 正式签约收购 Fin（原 Intercom），并入 Agentforce 体系，交易金额约 36 亿美元。因此本节与第2章 Agentforce 实质上正在成为同一技术谱系，两案例的相似之处更值得重视——不是巧合，而是这套设计范式正在成为行业整合后的统一标准。

## 3.1 核心机制

**三阶段架构**：Fin AI Engine 将每条消息处理为三个阶段——Refine Query（理解意图与上下文）→ Generate Response（检索相关知识并生成有依据的回答或动作）→ Validate Accuracy（发送前质量校验，若置信度不足则提出澄清问题或转人工）。这个结构与 Agentforce 的"检索→验证→决策"三段式高度一致。

**置信度驱动的诚实降级**：Fin 被设计为"不编造政策"——如果知识库没有覆盖某个问题，Fin 会选择升级而不是猜测，这被认为是它相较"看起来自信但可能说错"的传统 LLM 客服的核心差异化优势。

**宣传数据 vs 真实数据的落差（比 Zendesk 更详细的独立测算）**：官方宣称的解决率约 67%（部分场景宣传口径甚至到 76%），但第三方独立测算显示生产环境实际解决率通常在 45%-53%，个别小样本测试甚至只有 38%。差距的根源被归结为三点：对"工作流程特定问题"给出泛泛而答（第一大失败模式）、把有经验人工客服能当场解决的问题不必要地升级、知识库需要持续维护才能保持准确——**这三点本质上都指向同一个架构选择：Fin 是在查询时从知识库做检索，而不是从团队真实处理工单的历史方式中学习**。

## 3.2 与本项目架构的对照

| Fin AI 设计 | 本项目对应设计 | 差异 |
|---|---|---|
| Refine Query → Generate Response → Validate Accuracy | Planner Agent 规划 → Order/Logistics/Policy Agent 取证 → Decision Engine 融合裁决 | 结构思路一致，进一步印证"理解→取证/生成→校验"是行业收敛的通用范式，不只 Agentforce 一家如此 |
| 置信度不足时"诚实转人工"而非编造答案 | Reflection Trigger① Confidence Trigger | 思路一致，且 Fin 把这一点作为核心卖点单独强调，说明"不编造"本身就是客户愿意为之付费的能力，而不只是保底措施 |
| 生产环境解决率显著低于宣传数据（45-53% vs 67-76%），根源是纯检索式架构缺乏对本企业真实处理方式的学习 | 本项目 Mock Database 采用结构化事实字段（出库记录、多时间戳，见 `docs/02_DataDesign.md`），Decision Engine 基于 Business Rules + Evidence + Confidence 融合，而非单纯 RAG 检索知识库文本 | 印证了本项目"不能只靠知识库检索做决策"这一设计方向的合理性——检索式架构在"问答类"问题上表现尚可，但在"需要综合多方结构化证据做业务判断"（如退款决策）的场景上天然存在局限 |

# 4. Zendesk AI Agents

## 4.1 核心机制

**能力边界**：<cite index="14-1">Zendesk AI 更擅长基于知识库回答问题，在"处理退款、修改订单"这类需要真正执行动作的任务上相对偏弱，这类任务通常需要额外的自定义 API 开发才能实现。</cite>

**宣传效果 vs 真实效果的落差**：<cite index="14-1">Zendesk 官方宣传自主解决率最高可达 80%，但第三方评测与买家数据显示，真实场景下的自主解决率更常见于 10%-20% 区间，AI 实际上更多起到"分流"作用，而非"真正解决问题"。</cite>

**质量依赖知识库完备度**：<cite index="17-1">同样的知识库配置下结果差异很大——Edel Optics 仅通过接入实时客户数据这一项改动，AI 解决率就从 25% 跃升到 79%。</cite>

## 4.2 与本项目架构的对照

| Zendesk 现状 | 对本项目的启示 |
|---|---|
| 擅长"查知识库回答"，弱于"综合判断+执行动作"（如退款决策） | 本项目的核心场景恰好就是 Zendesk 的短板——不是"回答退款政策是什么"，而是"结合订单、物流、政策三方证据，判断这一单该不该退"，这正是 Evidence Fusion Decision Engine 要解决的问题，说明本项目场景选择有差异化价值，不是重复造一个知识库问答轮子 |
| 宣传解决率与真实解决率有明显落差 | 提醒本项目在 `docs/07_Evaluation.md` 阶段的 Success Metrics（如 Decision Accuracy > 90%）需要基于真实测试场景严格衡量，避免用"看起来能跑"的少数 Demo case 替代系统性评估 |
| 效果高度依赖接入数据的实时性和完备性 | 印证了本项目在 `docs/02_DataDesign.md` 中坚持"Mock Database 要有真实可计算的字段（如出库记录、多时间戳），而不是靠客户单方陈述"这一设计原则的必要性 |

# 5. 国内标杆案例

> 与 Salesforce/Zendesk 不同，国内案例更能验证本项目 Mock Database 与对话场景基于中文电商语境这一设计选择是否贴近真实产业实践。分传统时代与 LLM 时代两部分，资料主要来自 [chatbot-list](https://github.com/lizhe2004/chatbot-list)（GitHub 上一份持续维护的"智能客服/聊天机器人应用与架构分享"索引，1.4k Star）。

## 5.1 传统时代（2016-2020，规则/分类/知识图谱驱动）

### 阿里小蜜

来源：[拆开阿里小蜜的内核，看智能人机交互的实现逻辑（阿里云开发者社区）](https://developer.aliyun.com/article/105686)

**核心机制**：<cite index="26-1">阿里小蜜采用分领域分层分场景的架构抽象，将对话系统分为两层——意图识别层负责识别真实意图并做意图属性抽取，问答匹配层负责匹配问题并生成答案；针对电商场景中的三种典型问题类型采用不同处理路径：问答型（如"密码忘记怎么办"）用知识图谱+检索模型匹配，任务型（如订机票）用意图决策+槽位填充+深度强化学习，语聊型用检索模型与深度学习结合。</cite>

**对本项目的印证**：这个"先识别意图分类，再按类型分流到不同处理路径"的设计思路，与本项目 Planner Agent 判断请求类型后再分发给 Order/Logistics/Policy Agent 的思路方向一致——**说明"先分类、再分流"这个架构范式在规则驱动时代就已经是行业共识，不是 LLM 时代才有的新发明**。但阿里小蜜时代的"问答匹配"依赖预先构建的知识图谱和检索模型，本项目用 LLM 理解自然语言诉求、确定性规则引擎（`decision_rules.json`）做候选政策匹配和最终裁决替代了这套组合——同样不依赖语义检索，而是显式规则匹配，属于同一设计范式在不同技术底座上的实现。

### 京东 JIMI

来源：[京东JIMI 技术架构（简书）](https://www.jianshu.com/p/ba70f613c0c8)

<cite index="24-1">京东JIMI是电商客服机器人，累计服务用户已突破一亿。</cite>与阿里小蜜同属传统时代电商客服机器人代表，采用深度学习技术处理大量重复性客服请求。

## 5.2 LLM 时代（2024-2026，Agent / RAG 驱动）

`chatbot-list` 仓库专设"大模型时代 · 企业级实践"板块，收录了 2025-2026 年一批国内一线企业的 Agent 落地分享。其中阿里云的分享已找到公开转录全文，内容详实，单独展开；其余企业（快手、哈啰、B站等）仅有标题索引，列于第7章"研究边界"。

### 阿里云客服 Agent（AICon 2025 上海站，姜剑/飞樰）

来源：[阿里云客服Agent业务提效实践：灵活可控的落地方法论（InfoQ）](https://www.infoq.cn/article/vxqmohtlz9oasln733rg)

**Agent 模式分类**：演讲把当前 Agent 架构分为两大类——"大模型自主规划类"（如 Manus，灵活但可控性低，适合探索型、无既定解法的复杂问题）与"Workflow 预编排类"（灵活性较低但可控性高，**演讲原文点名 LangGraph 是这一类的典型代表**，适合标准化、重复性、周期性任务）。

**Multi-Agent 协同模式**：转交模式（A 处理完交给 B）、嵌套模式（A 调 B、B 调 C，逐层回溯，类似调用栈）、主代理 / Supervisor 模式（主 Agent 与客户交流，背后按需调度子 Agent）、群聊模式（多个 Agent 讨论后给出组合结论）。

**对本项目最具分量的一段论述**——关于"订单财务类"场景该用什么架构：

> 原文："像这种标准化场景，比如说我要去查订单有没有过期，或者我要计算有没有该退订的一些费用，该怎样给客户回复，这些都是要标准化的，如果你让大模型深度参与很容易出现幻觉……所以像这些场景，我们为了尽量避免出现这些问题，就通过 Workflow 的方式实现。"

与之相对，"RDS 实例异常诊断"这类问题描述模糊、排查路径不确定的场景，则被明确认为适合"大模型自主决策"。

**运行痛点（四类）**：① 提示词不稳定（过短/过长/前后矛盾导致模型顾头不顾尾，解法是用 AI 辅助生成和调优提示词，而非纯人工反复试错）；② Workflow 与大模型自主规划的权衡（可根据场景在两者间选型，也可以是"外部灵活、内部可控"的混合态，如邮箱诊断场景先用 Workflow 收窄范围、模型在其中自主决策具体路径）；③ 领域知识注入（通用模型缺乏领域知识，通过动态加载 Prompt、外部知识库、必要时训练领域大模型解决）；④ 响应速度（大参数模型效果好但慢，小参数模型快但效果一般，可用模型蒸馏、量化、KV Cache 优化折中）。

**Agent 平台调优路径**：从"提示词工程调原型"，到"效果不够拆解为 Workflow"，到"仍不够则拆解 Multi-Agent 做指令设计"，到"最后才考虑模型训练调优"——**是一条成本递增、效果也递增的路径，不是一上来就选最复杂的方案**。

### 对本项目的印证

| 阿里云实践 | 本项目对应设计 | 印证 |
|---|---|---|
| Workflow 预编排类的典型代表点名 LangGraph | 本项目技术选型为 LangGraph（见 `docs/04_Architecture.md`） | 直接印证：本项目选择的技术栈在国内一线大厂的 Agent 分类方法论里，正是"标准化、可控业务场景"的推荐选型，而不是拍脑袋选的框架 |
| **"订单财务类标准化场景，大模型深度参与容易出现幻觉，应通过 Workflow 方式实现"** | Evidence Fusion Decision Engine 采用 **Business Rules + Evidence + Confidence** 融合，而非让 LLM 自由裁决（见 `docs/04_Architecture.md` 3.3节） | **这是本次调研中分量最重的一条印证**——阿里云 7 年一线算法专家明确指出"退款费用计算"这类场景不能让大模型深度自由判断，必须用结构化方式约束，与本项目"不能让 LLM 随意判断"这一设计初衷逐字对应，且来自实际生产环境踩坑后的方法论总结，不是理论推演 |
| Multi-Agent 的"主代理/Supervisor 模式" | Planner Agent 统筹、按需调度 Order/Logistics/Policy Agent，Decision Engine 汇总裁决 | 本项目架构是 Supervisor 模式的一种具体实现，非本项目自创的模式 |
| 提示词不稳定、Workflow 与自主规划的权衡、领域知识注入、响应速度四类真实痛点 | 对应本项目在 `docs/05_DecisionRules.md`（声明式规则替代不稳定提示词）与 `docs/06_LowLevelDesign.md`（各节点 State/Prompt 契约）中的应对设计 | 这四类痛点在实现阶段确实都命中过：声明式 JSON 规则替代了让 LLM 直接判断退款金额、`evidence_gate.py` 用显式状态机约束节点间流转，而不是让模型自主规划下一步 |

# 6. 标杆调研对本项目架构决策的印证总结

对照标杆产品的实际做法，本项目在 `docs/04_Architecture.md` 中的几个关键决策得到不同程度的印证：

1. **置信度驱动升级 + 硬性规则优先**：与 Agentforce、Fin AI 的设计思路高度一致，是行业验证过的成熟模式，不是本项目自创的过度设计
2. **按数据来源拆分 Agent，而非单一推理引擎内部处理**：Salesforce/Zendesk/Fin 都倾向于用单一推理引擎（内部封装检索/验证/决策），阿里小蜜时代虽有"意图识别层/问答匹配层"的分层，但也不是显式拆分为多个独立 Agent。本项目选择显式拆分为多个职责独立的 Agent，牺牲了一定的实现简洁性，换来的是**决策过程的可审计性**——这与 PRD 中"可解释性"非功能需求的定位一致，也是本项目区别于"调用现成客服 AI 平台"的核心价值主张
3. **场景选择的差异化**：Zendesk 的短板（知识库问答强、决策执行弱）恰好是本项目的核心场景，说明选择"退款/售后决策"作为切入点，而非"知识库问答"，是有意义的差异化定位，不是重复造轮子
4. **评估方法论的警示**：Zendesk、Fin AI"宣传数据 vs 真实数据"的落差（Zendesk 80% vs 10-20%，Fin AI 67-76% vs 45-53%），提醒本项目在 `docs/07_Evaluation.md` 阶段要用真实、系统性的测试场景衡量 Success Metrics，避免仅用几个精心挑选的 Demo case 得出过于乐观的结论
5. **技术选型时间点的合理性**：国内头部企业 2025-2026 年密集转向 Agent 化客服架构，本项目的 LangGraph + LLM Agent 技术路线与行业实践节奏同步，不是超前的实验性选择，也不是滞后的过时方案
6. **技术框架选型的直接背书**：阿里云算法专家在方法论分享中明确把 LangGraph 归为"Workflow 预编排类"的典型代表，并指出这类框架适合标准化、可控性要求高的业务场景——与本项目的场景定位（退款决策需要高可控性，不适合完全交给大模型自主规划）完全吻合
7. **本项目核心设计原则的一手佐证（分量最重）**：阿里云 7 年一线算法专家明确指出"订单财务类标准化场景（如计算退款费用），若让大模型深度参与容易出现幻觉，应通过 Workflow 方式实现"——这与本项目 Evidence Fusion Decision Engine 坚持"Business Rules + Evidence + Confidence 融合，而非 LLM 自由裁决"的设计初衷逐字对应，且这一结论来自生产环境踩坑后的方法论总结，而非本项目自行推断
